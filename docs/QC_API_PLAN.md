# Learn and expose the Quad Cortex API

Tone Lab should own the Quad Cortex interface its desktop, scripts, and agents use. Start by mapping what existing code and documentation already cover. Use ordinary Cortex Control and hardware actions to learn the gaps on this Windows setup. Publish the findings as a versioned capability catalog, and promote operations into the app as their behavior becomes repeatable. The target is every observable operation relevant to the rig, with a clear answer for each item that remains unknown or requires the official editor.

## What we have

| Surface | Starting evidence | Role in Tone Lab |
| --- | --- | --- |
| USB and DIN MIDI | Neural DSP documents incoming messages and preset MIDI out. [Quad Cortex manual](https://neuraldsp.com/manual/quad-cortex) | Use documented performance controls where they fit. Measure what feedback the rig actually emits. |
| USB audio | Neural DSP documents routing, recording, reamping and host monitoring. [USB audio guide](https://neuraldsp.com/getting-started/using-quad-cortex-as-an-audio-interface) | Keep audio streaming separate from editor commands. Measure channel selection, continuity and latency alongside control experiments. |
| Cortex Control USB HID | The pinned Python package includes a device library, protocol code, versioned descriptors and a model catalog. Its MCP server is one consumer. The upstream Windows docs report shared-handle reads and a parameter write on CorOS 4.1.0. [qc-mcp](https://github.com/lexasoft123/qc-mcp) · [Windows results](https://github.com/lexasoft123/qc-mcp/blob/main/docs/WINDOWS.md) | Compare the pinned library, current upstream, and independent implementations. Treat shared transport and safe concurrent editing as separate experiments. [Independent Cortex client](https://github.com/pacharanero/cortex) |
| Exported files and local backups | Cortex Control documents user-content transfer and local backups. Tone Lab already has a test that accepts a corpus of preset protobuf files. [Quad Cortex manual](https://neuraldsp.com/manual/quad-cortex) · [Preset contract test](../tests/test_lab_sim_contract.py) | Develop read-only inspection and dependency reports from export copies. Verify what backups include before relying on them for recovery. |

Today [device.py](../lab/qc/device.py) blocks access while Cortex Control is running. The existing `TONE_LAB_TRACE` records Tone Lab's device calls and replies, which [the simulator contract tests](../tests/test_lab_sim_contract.py) can replay offline. Discovering editor traffic needs a separate observation path. Keep the pinned adapter working while filling gaps. Check licensing before incorporating any upstream code, descriptors or catalog data into the public repo.

## Build the catalog

1. **Inventory offline.** Compare everything in the pinned library, descriptors, model catalog and protocol notes with Tone Lab's call sites and the exposed MCP tools. Separate capabilities already decoded but unwired from those needing discovery. Use the official editor and hardware feature lists as a checklist, including actions with no known protocol mapping. Record source and version for each result.
2. **Observe normal operation.** In an explicit bench session, log idle behavior and the initial device/editor connection. Capture one labeled editor or front-panel action at a time on a disposable preset. Make the change, undo it, and repeat it from a known starting state. Compare device replies, unsolicited events, and before/after snapshots. Try a passive shared HID observer on Windows for incoming reports. Where outbound evidence matters, use a short, device-scoped USB trace of the official editor. Keep raw traces, backups, and real inventory under the Tone Lab data folder or git-ignored `personal/`. Check the ignore rule before writing there.
3. **Explain what changed.** Automate decoding and a semantic diff. Normalize volatile IDs and timestamps, preserve command ordering, and distinguish acknowledgement, state events, readback, and background refresh. Repeat representative actions at different values and in different scenes or modes to recover units, limits, enum labels, and scope. Save synthetic fixtures that exercise the same shape. For export decoding, preserve unknown fields and confirm that a representative copy round-trips before considering any writer.
4. **Verify and promote.** Use known commands and valid values for bench checks. Test incomplete replies, disconnects, and unknown fields in the simulator. For a write, verify what actually changed on the unit and what persisted after reopening the preset. Record failures and unexplained effects in the catalog before exposing the operation. Recheck affected capabilities when CorOS, Cortex Control, the driver, or the protocol adapter changes.

Each catalog row should name an action or observable field, its source and transport, request and response types, units and valid values, affected scope, persistence, prerequisites, and how fresh state is obtained. Record firmware, editor and adapter versions, evidence links, representative latency where it matters, and a fixture reference. Track evidence as **documented**, **decoded**, **observed**, or **repeatable**. Record **supported**, **editor-only**, **unavailable** or **unknown** separately so that discovery does not automatically enable a write. Generate the human-readable coverage report from the same manifest the app and CLI query.

## Research order

| Priority | What to learn | What it unlocks |
| --- | --- | --- |
| 1 | Firmware and schema identity, current preset and scene, unsaved edits, tempo, mode, active routing, and external change events | See what the player is doing on the QC or in Cortex Control. Invalidate stale plans and resume safely after a handoff. |
| 2 | Model IDs, parameter names and ranges, scene and bypass behavior, device presets, plugin device availability, IRs and captures, and which assets a preset references | Build richer tones from blocks and assets actually available on this unit. Explain missing dependencies and snapshot a reference preset. |
| 3 | Graph edits, splits and mixers, scene-specific settings, expression and stomp assignments, MIDI mapping, tempo and CPU limits | Build playable multi-scene presets and batch live tone controls with consistent readback. |
| 4 | I/O levels and metering, USB dry/wet and reamp routing, global EQ scope, and route changes during playback | Verify gain staging and measure reamp behavior without disturbing the player's monitoring. Establish global behavior before considering edits. |
| 5 | Preset and setlist operations, capture and IR import/export, folder moves, backup contents, and asset identity across exports | Keep Tone Lab tones in their own QC area and retain portable copies and references. Distinguish the same name from the same asset. |
| 6 | Other editor and hardware features such as tuner, looper, mode changes, and capture workflows | Close out the coverage report with a supported operation, editor workflow, or known gap for each feature. |

Leave firmware installation, factory reset, whole-device restore, and account and licensing operations in the official workflow. Record what the device exposes about them. Internal DSP algorithms and state that never leaves the unit are outside the measurable coverage target.

## Keep Cortex Control usable

Start by proving observation with the editor open. Compare a passive mirror with explicit read queries and identify which state updates reliably arrive. Check request/reply correlation when Cortex Control is busy. When the state is stale or incomplete, say so and refresh on reacquiring the connection. Avoid a high-rate poller competing with recording or playback.

Use the existing [Host](../lab/qc/host.py) as the broker for Tone Lab clients and [Unit](../lab/qc/unit.py) as the single write boundary. Give each snapshot a revision tied to preset, scene, connection and relevant state. A plan carries the revision and target it was built for. Re-read before applying it and discard the plan if the player has changed the target. For operations where an external change could arrive between checking and writing, require a verified exclusive handoff. Initially use short exclusive batches for edits, and confirm routing and the original player selection when giving control back. Only allow shared editing for individual operations whose conflict behavior passes bench checks. Test editor startup, manual changes on the QC, simultaneous requests, interrupted builds and reconnects.

Keep writes in verified Tone Lab slots. Route and level changes must preserve the output ceiling, set levels before connecting inputs, and read back applied state. A timed-out save gets reconciled against the device directory before it is retried. If the device disappears mid-operation, stop audio safely and reconcile on reconnect before accepting further edits. Keep persistent saves separate from audition edits and preserve the player's baseline. Read-only operation can remain available for a new firmware version wherever the results can be decoded and verified.

## Expose it once

Build a typed local Python interface and a small CLI with readable and JSON output. Start with `capabilities`, `snapshot`, `watch`, `catalog` and `diff`. Add `preview_changes`, `apply_if_revision`, `audition`, `reamp` and `save_copy` as the relevant write families become verified. Return measured state, provenance, freshness and concrete errors. Keep a transport adapter under that interface so the currently pinned package can be supplemented or replaced without changing the app. Favor a compatible fix or small licensed subset over maintaining a full fork.

Make MCP an optional client of that same interface. Agents get read-only resources for state, capabilities and asset schemas, plus typed tools for bounded intent such as auditioning a chain or saving a copy to Tone Lab's setlist. The desktop uses the same API and can batch knob updates locally. Raw HID, per-audio-buffer control, and maintenance operations stay outside the agent surface. Keep detailed block editing in Cortex Control and surface only the capabilities that help the player express or test an intent in Tone Lab.

## First milestone and acceptance

1. **Offline milestone.** Produce the first manifest and gap report from the installed library, current upstream and the app. Add synthetic replay and a read-only diff command that works without a QC.
2. **First bench session.** Record idle and reconnect baselines and about a dozen actions covering preset selection, scene change, an unsaved knob edit, bypass, tempo, block add or move, an IR selection, and a save to a disposable slot. Repeat representative actions on the device and editor. Use those results to prove a read-only `watch` that identifies the action and marks stale state. This session can run with outputs muted and without guitar playing.
3. **First useful write slice.** Preview and audition a small chain with a verified scene change and parameter edit in a Tone Lab slot. Show that an intervening player edit invalidates the plan. Verify clean handoff, cancellation, repeated reopen and save readback. Run the record/reamp path alongside monitoring to check audio continuity and measure control latency.
4. **Expand by family.** Publish which checklist items have versioned evidence and which remain unknown. Each supported family needs simulator coverage, bench evidence, and the same behavior through desktop, CLI and MCP where exposed. On firmware updates, rerun the smoke checklist on the owned rig and restore writes family by family as needed.
